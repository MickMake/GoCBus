# GoCBus v0.42.6 - Lighting transmit and PCI initialisation Design

## Status

**Release:** v0.42.6  
**Parent release:** v0.42  
**Design status:** Planned  
**Dependencies:** v0.42.2-v0.42.5

## Objective

Send Lighting commands reliably through an initialised PCI/CNI and make command success/failure observable.

## Owned areas

- `internal/lighting/`
- `internal/protocol/`
- `internal/transport/`

These directory boundaries are part of the v0.42 design. A slice may use public interfaces from earlier slices, but it should not casually move another slice's responsibility into its own package.

## Scope

- PCI reset and minimum interface configuration required by GoCBus.
- Lighting ON/OFF/RAMP encode and send.
- Terminate-ramp if practical.
- Confirmation-code allocation/matching.
- Send pacing/back-pressure required by physical PCI behaviour.

## Design rules

- Keep the implementation idiomatic Go rather than translating Python structure line-for-line.
- libcbus is the behavioural/protocol reference, not a runtime dependency.
- Prefer explicit small types and interfaces over framework-style abstractions.
- Unknown or unsupported protocol input must remain observable.
- Tests should be deterministic and should use captured/known protocol fixtures where possible.
- Any deviation from this design must be recorded in `docs/v0.42/ImplementationState.md` before the slice is considered complete.

## Deliberate non-goals

- Do not add MMI/state synchronisation yet.
- Do not expose MQTT controls.
- Do not reproduce unused libcbus PCI options.

## Exit criteria

- Commands can be issued against hardware or a protocol fixture.
- A command has an explicit confirmed/failed/timeout result.
- Initialisation is repeatable after reconnect.

## Reference material

Primary reference is Michael Farrell's `micolous/cbus` / libcbus, particularly the files relevant to this slice. Translate behaviour and protocol knowledge into Go; do not preserve Python architecture merely for familiarity.

## Completion record

When implemented, update `docs/v0.42/ImplementationState.md` with:

- completion status,
- files/packages actually created,
- tests added,
- discoveries,
- deferred issues,
- any variation from this design.
