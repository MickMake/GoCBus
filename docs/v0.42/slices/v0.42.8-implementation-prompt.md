## Objective

Maintain the best-known C-Bus Lighting state and reconcile startup/status snapshots with live SAL events.

## Scope

- Explicit UNKNOWN, known OFF and known level/on states, with freshness/validity tracked separately from the value.
- Canonical state identity that preserves the C-Bus context required to distinguish network/application/group; a bare group number is not assumed globally unique.
- Per-group local ordering metadata and synchronisation generation/dirty tracking.
- Startup synchronisation state.
- Merge live events with binary/level status responses.
- Protection against an older/current-generation snapshot overwriting a newer live event.
- Reconnect semantics: retain last-known values only as stale/non-authoritative until new evidence confirms them.
- Periodic/passive reconciliation hooks.
- Ramp target/transition representation without pretending an estimated level is authoritative.

## Owned areas

- `internal/state/`

## Constraints

- No MQTT-specific retained-state behaviour.
- No UI concepts.
- No guessing unknown groups as OFF.

Additional constraints:

- Binary name is `GoCBus` wherever this slice touches executable naming.
- Do not introduce C-Gate as a dependency.
- Slice 8 is an intentional architectural departure from libcbus's event-driven state model.
- Use libcbus as the behavioural reference for incoming Lighting and status semantics, but do not reproduce its long-lived state-management architecture.
- GoCBus must explicitly solve startup state recovery, reconnect recovery, and stale status/live-event reconciliation.
- Each status synchronisation attempt has a local generation. If a group receives a live SAL event after that generation begins, status data from the same generation must not overwrite the live event unless protocol/hardware evidence provides a stronger ordering guarantee.
- Transport loss invalidates freshness, not historical knowledge: last-known values may be retained for diagnostics but must not be treated or republished as freshly confirmed after reconnect until new live/status evidence arrives.
- Preserve proven libcbus protocol semantics unless a documented corrective deviation is required.
- Do not translate Python structure line-for-line; implement the behaviour using the simplest idiomatic Go structure.
- Keep public APIs as small as practical.
- Prefer table-driven tests and captured fixtures.
- Do not begin the next slice as a "small extra".
- Update `docs/v0.42/ImplementationState.md` with actual implementation status, discoveries, deferrals and design variations before opening the PR.

## Exit criteria

- Incoming Lighting/status semantics inherited from libcbus remain equivalent except for explicitly documented corrective deviations; state-management behaviour is intentionally not required to match libcbus.
- Restart can rebuild current Lighting state without waiting for every switch to be used.
- A live event during sync wins over an older status snapshot.
- Same-number groups in distinct state identities cannot collide in the state store.
- Reconnect tests prove stale pre-disconnect values cannot become freshly authoritative without new evidence.
- State transitions carry a reason/source suitable for diagnostics.

## Evidence and synchronisation acceptance

- Use Slice 7's attribution evidence; a new generation must not make an old or unattributable report fresh. Test a live OFF between queries A and B followed by a delayed ON reply to A.
- Before completion, record expected group/block coverage, bounded sync completion/retry policy, binary-only fallback, and the criteria for SYNCING, UP and DEGRADED. Keep connection health distinct from state coverage.
- Missing/unresponsive groups must not keep one attempt open forever or become OFF by default. Publish known groups progressively; uncertain fields stay unknown/stale.
- Record and test a compact merge table for binary ON/OFF, numeric level, MISSING/ERROR or invalid level evidence, ramp start/interruption/termination, and transport loss.
- Fresh binary ON can confirm on/off without refreshing an old brightness. Confirm only fields supported by the evidence; a ramp target/estimate is not a confirmed instantaneous level.
- When freshness cannot be established, retain uncertainty and schedule bounded reconciliation rather than guessing. Record hardware-dependent limitations and the evidence needed to resolve them.

When complete, summarise what changed, tests run, known issues, and any design variation. Then open a PR against `main`.
