# GoCBus v0.42.7 - Status and MMI Design

## Status

**Release:** v0.42.7  
**Parent release:** v0.42  
**Design status:** Planned  
**Dependencies:** v0.42.4-v0.42.6

## Objective

Implement the C-Bus status mechanisms needed to discover current Lighting state instead of relying only on live events.

## Owned areas

- `internal/status/`

These responsibility boundaries are part of the v0.42 design. The exact Go package topology may be simplified where implementation evidence supports it, provided responsibilities remain clear and the variation is recorded in `ImplementationState.md`.

## Scope

- Lighting status request SAL.
- Binary status report decoding.
- Level status report decoding.
- Manchester encoding/decoding required by level reports.
- Status block addressing and assembly across multiple responses.

## Design rules

- Keep the implementation idiomatic Go rather than translating Python structure line-for-line.
- libcbus is the behavioural baseline for protocol behaviour in this slice.
- Preserve its proven observable behaviour unless a documented corrective deviation is required.
- Implementation structure should be idiomatic Go and need not resemble the Python architecture.
- Prefer explicit small types and interfaces over framework-style abstractions.
- Unknown or unsupported protocol input must remain observable.
- Tests should be deterministic and should use captured/known protocol fixtures where possible.
- Any material design variation or behavioural deviation from libcbus must be recorded in `docs/v0.42/ImplementationState.md` before the slice is considered complete.

## Deliberate non-goals

- Do not decide authoritative current state; that belongs to v0.42.8.
- Do not yet expose status through MQTT.
- Do not broaden into unrelated CAL applications.

## Exit criteria

- Behaviour migrated from libcbus has equivalent observable results except for explicitly documented corrective deviations.
- Known libcbus binary and level status fixtures decode equivalently.
- A complete Lighting status query can be represented and its replies assembled.
- Partial/missing blocks remain explicitly incomplete.

## Status attribution acceptance

- A local synchronisation generation is not a wire transaction identifier. Preserve available application/block/source context and record what can actually establish response attribution/freshness.
- Start with non-overlapping status queries; document handling of delayed, duplicate and unsolicited reports, partial blocks, and cancellation on disconnect. Serialisation alone is not proof of freshness.
- Establish bounded query completion and record missing coverage for Slice 8. Choose timings from protocol/hardware evidence rather than assuming every group responds.
- Test query A timing out, query B starting, and a late reply to A arriving. The result must retain attribution uncertainty where it cannot be resolved, rather than silently treating arrival during B as proof of freshness.
- Expose completion/uncertainty to Slice 8 without deciding authoritative group state here.

## Reference material

Primary reference is Michael Farrell's `micolous/cbus` / libcbus at pinned v0.42 commit `cc0bdf3a25bd5646dd2d8e7d88a46fcd198f53a1`, particularly the files relevant to this slice. Translate behaviour and protocol knowledge into Go; do not preserve Python architecture merely for familiarity.
