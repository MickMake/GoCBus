# GoCBus v0.42.13 - Operational control and status Design

## Status

**Release:** v0.42.13  
**Design status:** Planned

## Objective

Provide one coherent runtime control/status surface while keeping C-Bus lifecycle and MQTT connection state explicitly separate.

## Owned areas

- `internal/control/`
- `internal/runtime/`
- `internal/homeassistant/`

## Scope

- C-Bus lifecycle states DOWN, CONNECTING, INITIALISING, SYNCING, UP, PASSTHROUGH, DEGRADED, ERROR.
- Separate MQTT connection state, initially kept small (for example DOWN, CONNECTING, UP, ERROR).
- MQTT/HA status sensor exposing both subsystem states.
- Passthrough, debug/raw logging, force-resync and safe reconnect controls.
- Last-message/sync timestamps and useful counters.

## Design rules

- Where this slice migrates behaviour that already exists in libcbus, use libcbus as the primary behavioural baseline and preserve its proven observable behaviour unless a documented corrective deviation is required.
- Implementation structure should be idiomatic Go and need not resemble the Python architecture.
- Keep interfaces small and unknown protocol input observable.
- Do not force orthogonal subsystem failures into a single lifecycle enum; any overall health indicator must be derived from subsystem truth rather than replacing it.
- Record any material design variation or behavioural deviation from libcbus in `docs/v0.42/ImplementationState.md`.

## Deliberate non-goals

- Do not expose every internal boolean.
- Avoid contradictory flags.
- Controls use explicit APIs.

## Exit criteria

- Any behaviour migrated from libcbus has equivalent observable results except for explicitly documented corrective deviations.
- Operator can identify C-Bus lifecycle state and MQTT connection state independently.
- Approved HA/MQTT controls work safely.
- Transitions are logged and testable.

## Completion record

Update `ImplementationState.md` with completion, tests, discoveries, deferrals and design variations.
