# GoCBus v0.42.8 - State engine Design

## Status

**Release:** v0.42.8  
**Parent release:** v0.42  
**Design status:** Planned  
**Dependencies:** v0.42.5-v0.42.7

## Objective

Maintain the best-known C-Bus Lighting state and reconcile startup/status snapshots with live SAL events.

## Owned areas

- `internal/state/`

These directory boundaries are part of the v0.42 design. A slice may use public interfaces from earlier slices, but it should not casually move another slice's responsibility into its own package.

## Scope

- Explicit UNKNOWN, known OFF and known level/on states.
- Per-group ordering/version metadata.
- Startup synchronisation state.
- Merge live events with binary/level status responses.
- Protection against older snapshot data overwriting newer live events.
- Periodic/passive reconciliation hooks.
- Ramp target/transition representation without pretending an estimated level is authoritative.

## Design rules

- Keep the implementation idiomatic Go rather than translating Python structure line-for-line.
- Slice 8 is an intentional architectural departure from libcbus's event-driven state model.
- Use libcbus as the behavioural reference for incoming Lighting and status semantics, but do not reproduce its long-lived state-management architecture.
- GoCBus must explicitly solve startup state recovery, reconnect recovery, and stale status/live-event reconciliation.
- Preserve proven libcbus protocol semantics unless a documented corrective deviation is required.
- Implementation structure should be idiomatic Go and need not resemble the Python architecture.
- Prefer explicit small types and interfaces over framework-style abstractions.
- Unknown or unsupported protocol input must remain observable.
- Tests should be deterministic and should use captured/known protocol fixtures where possible.
- Any material design variation or behavioural deviation from libcbus must be recorded in `docs/v0.42/ImplementationState.md` before the slice is considered complete.

## Deliberate non-goals

- No MQTT-specific retained-state behaviour.
- No UI concepts.
- No guessing unknown groups as OFF.

## Exit criteria

- Incoming Lighting/status semantics inherited from libcbus remain equivalent except for explicitly documented corrective deviations; state-management behaviour is intentionally not required to match libcbus.
- Restart can rebuild current Lighting state without waiting for every switch to be used.
- A live event during sync wins over an older status snapshot.
- State transitions carry a reason/source suitable for diagnostics.

## Reference material

Primary reference is Michael Farrell's `micolous/cbus` / libcbus, particularly the files relevant to this slice. Translate behaviour and protocol knowledge into Go; do not preserve Python architecture merely for familiarity.
