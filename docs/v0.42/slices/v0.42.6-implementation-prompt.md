## Objective

Send Lighting commands reliably through an initialised PCI/CNI and make command success/failure observable.

## Scope

- PCI reset and minimum interface configuration required by GoCBus.
- Lighting ON/OFF/RAMP encode and send.
- Terminate-ramp if practical.
- Confirmation-code allocation/matching.
- Explicit distinction between interface/protocol confirmation and observed Lighting/group state.
- Send pacing/back-pressure required by physical PCI behaviour.

## Owned areas

- `internal/lighting/`
- `internal/protocol/`
- `internal/transport/`

## Constraints

- Do not add MMI/state synchronisation yet.
- Do not expose MQTT controls.
- Do not reproduce unused libcbus PCI options.

Additional constraints:

- Binary name is `GoCBus` wherever this slice touches executable naming.
- Do not introduce C-Gate as a dependency.
- Use libcbus as the primary behavioural baseline for protocol behaviour in this slice.
- Preserve proven observable behaviour unless a documented corrective deviation is required.
- A successful confirmation must not, by itself, mutate authoritative group state; state requires live SAL/status evidence or another explicitly validated protocol guarantee.
- Do not translate Python structure line-for-line; implement the behaviour using the simplest idiomatic Go structure.
- Keep public APIs as small as practical.
- Prefer table-driven tests and captured fixtures.
- Do not begin the next slice as a "small extra".
- Update `docs/v0.42/ImplementationState.md` with actual implementation status, discoveries, deferrals and design variations before opening the PR.

## Exit criteria

- Behaviour migrated from libcbus has equivalent observable results except for explicitly documented corrective deviations.
- Commands can be issued against hardware or a protocol fixture.
- A command has an explicit confirmed/failed/timeout result.
- The confirmed result is documented as an interface/protocol outcome, not proof that the physical load reached the requested state.
- Initialisation is repeatable after reconnect.

## Command lifecycle acceptance

- Extend the working receive path into a self-initialising live Lighting demonstration; transport/protocol reception must be able to consume initialisation replies.
- Use one owner for physical writes and pending confirmations. Bound pending work and define explicit back-pressure/overflow outcomes.
- Before completion, record confirmation-code reuse, late-reply matching, timeout and disconnect policies with protocol/hardware evidence where needed.
- A timeout can leave execution unknown. Do not automatically replay uncertain commands; any retry rule must justify its command semantics and prevent stale confirmations completing new work.
- Test a late confirmation after timeout/code reuse, disconnect with pending work, and cancellation without leaked readers/writers. Reconnect must not silently replay old commands.

When complete, summarise what changed, tests run, known issues, and any design variation. Then open a PR against `main`.
